# Contributing

Useful contributions improve a concrete editorial decision or observable behavior.
An issue can describe a confusing instruction, lost voice, unsupported format,
incorrect timing assumption, broken dependency, or reproducible CLI problem.

For code changes, use Python 3.10+ standard-library features, keep the helper usable
without installation, and add a behavior test when a bug or invariant justifies it.
Run the unit suite and tools/verify_project.py. Preserve raw drafts and explicit
constraint semantics. Do not silently add network calls, models, or dependencies.

For editorial changes, provide the actual writing context, the previous behavior,
the proposed behavior, and its tradeoff. An example can show a clearer expectation
or repaired callback without claiming more laughs. Keep small requests small.
Do not turn one project's preference into a rule for every language or comic form.

For audience claims, distinguish observed feedback from model-generated opinion.
Document version, delivery, audience context, presentation order, and limitations.
Do not submit private drafts, personal recordings, copied routines, scraped joke
corpora, or excerpts you cannot share. New research sources need URLs, access dates,
reuse status, and a clear explanation of what they change.

Original contributions are submitted under the project's MIT license. State whether
AI helped produce the contribution when that information is material to review.
Use issues and pull requests for substantive changes; no contribution is automatically
accepted because a model or a technical check assigned it a high score.
